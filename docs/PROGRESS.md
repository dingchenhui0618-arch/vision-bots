**新增第四档 repair：respeak（重说）**：「指纹住在→专注在」删 3 补 2，等字数替换/补字/删字三档都装不下。
整段塌成一个词，只吃整词、最多 3 个词，新词起点=第一个被吃词的起点（句子起点不动），
落地后整句必须逐字等于音频，否则整处撤回。

**这一轮抓到的两个自己造成的坑**：
- 逐词层把对的原判「AI时代」（「时」p=0.23）改成同音「是」，交付字幕变成「AI是代」——
  同音规则只看一个字，看不见「时代」是个词。新增**分词判据**：改完把整词切碎的一律打回（ICU 分词，和断行同一套）。
- 重剪时耳朵定过的句子会被重新排序、有时不再被选中，修好的字会退回去；新增 relisten-carry.json（合并式累积），
  重剪先把这些句子按音频再确认一遍。质检线索写文件的 `audioReview.text` 无条件下标也会抛异常，
  导致线索一条都写不出去（静默失败），已修。

**质检口径再收紧一条**：语义建议在「听音复核两次听不一致 / 没跑成」时**不许拦交付**，只记为疑似。
实测同一部片子连跑两轮质检，同一处一轮拦一轮不拦，差别全在这一次解码像不像——拿它当闸门，闸门就是随机的。

**结果（自测15）**：成片 66.53s / 1080×1920 / 1996 帧 / −14.8 LUFS；改好 7 处（AI时代、大家、专注在、知道的人、
卷技术、卷内容、GPT/Claude/Codex）；没把握 12/248 = 4.8%（自测14 是 7.9%）；质检 18/18。

## 里程碑 4 · 光轨模板（2026-11-20）

第二个模板按「引擎代码 + template.json，内容 = scene.json」落地，但它不是 ASS 字幕，是**逐帧渲染**：
canvas 引擎跑在无头 Chrome 里，成片每一帧都是 `scene.json` + 时间的纯函数。

**结构**
- `vendor/lighttrail/`：上游引擎（engine/ + tools/render.mjs）以副本引入，补了两个参数：`--fonts`（字体 18MB 不进仓库）和 `LIGHTTRAIL_FFMPEG`（本机 ffmpeg 不在 PATH 上）。
- `templates/lighttrail/scene.mjs`：词级时间戳 + EDL → scene（卡片逐字落点、章节、光轨刻度、音效 cue）。模型不参与任何数字。
- `templates/lighttrail/film.js`：数据驱动的画面。一线到底（点燃 → 扫描 → 声波基线 → 收成一个点）、整句大字逐字翻白、章节齿、`REC 时间码`、`01/05`、`素材 24.9s · 剪掉 8.1s · 6 段`。
- `templates/lighttrail/render.mjs`：抽帧 → 切音 → 包络 → 逐帧渲染 → 音效 → 混音 → 编码。
- `src/sfx.mjs`：音效按 cue 本地合成，无样本文件（click / zip / scan / blip / impact / drop）。
- `pack.mjs` 按模板的 `engine` 分派：`ffmpeg`（ASS 构图）和 `canvas`（逐帧）。

**实测**（24.93s 素材 → 16.72s 成片，503 帧，1080×1440@30）
- 抽帧 5.4s / 逐帧渲染 53.1s / 编码 16.9MB / 响度 −17.2 LUFS / 质检 6/6。
- 渲染吞吐 **0.32× 实时**。上一轮记的 1.68 fps 是上游那条满是点云和缩略图的 showreel，不是这个模板——产品化估算要按模板分。
- 关掉渐变颗粒后 crf 23 只有 3.5MB，crf 19 是 65.6MB；因此定 `crf 20 + maxrate 8M`，颗粒从 0.035 降到 0.026。

**踩到的坑**
- 抽帧用 `-t` 按秒切，每段 ffmpeg 各自四舍五入，累计多出一帧，成片帧 → 源帧整体错位；改成 `-frames:v srcCount` 精确控制，帧号必须和 scene 里的 `ranges` 逐段对齐。
- `writeFileSync(path, buffer, { encoding: 'buffer' })` 不是合法编码，直接抛 `ERR_UNKNOWN_ENCODING`；WAV 要 `Buffer.concat([header, pcm])`。
- 图片导出用了相对路径，ffmpeg 的工作目录不是项目根，报 `No such file or directory` 而不是报路径错；一律用绝对路径。
- 逐帧渲染器默认 `spawn('ffmpeg')`，本机 ffmpeg 在 WinGet 目录里不在 PATH 上，引擎直接 ENOENT；用环境变量把解析好的路径传进去。
- 用 PowerShell 的 `Set-Content -Encoding UTF8` 改 group.json，Windows PowerShell 5.1 会写 BOM，JSON.parse 直接抛错，整个群打不开（/file 也跟着 500）。**改 JSON 一律用 Node，不用 PowerShell 写。** 这个坑在本项目是第二次踩。

**没做的**
- 「字藏人物身后」要人物蒙版，上游用 macOS Vision 出 matte，Windows 上还没有替代实现——现在大字压在人物前方，靠大字区间压光保证可读。
- 光轨只有 3:4；9:16 要重排大字区间与光轨高度。

## 里程碑 5 · 错字治理与分章（2026-11-20）

上一轮交付的字幕里「观众三秒就**画**走了」原样发出去了，质检也查不出来——这一轮把它补上。

**错字治理：两层，都在剪辑阶段**
- 热词注入：`config/terms.json` 的术语表进 faster-whisper 的 `initial_prompt`。
- 受约束纠错：术语表确定性替换 + 模型按词位索引提案 → 校验器。模型说的不算数，过校验才算改。
- 校验器四类放行（同音字查拼音、专有名词查术语表、数字只修阿拉伯数字写错、标点不需要）、六类打回（字数变了 / 词位越界 / 同词位改两次 / 塞空格 / 改完没变 / 不在四类里）。
- 硬约束：只改词文本。词数与每个词的 start/end 由模块内部断言，动了直接抛错中止。
- 术语表支持 `next` 限定：单字条目靠后一个词定位（「化」+「走」→「划」，「减」+「删」→「剪」），用来修被 ASR 拆成两个词的错。
- 没有 pypinyin 时进保守模式：只做术语表和数字，模型提的同音改动一律不采纳。

**分章**
- `src/chapters.mjs`：残句（不到 4 字或不到 1 秒）并进上一章；短章可以并，但并完超过 20 字不并。两个模板共用。
- 光轨的退路从「两张卡片一章」改成按字数预算攒。旧规则在这条素材上攒出 19/25/25/3 字四章——两堵三行墙，加一个只闪一帧的「这件事」。
- 大字窗口从「字数 × 0.16s」改成「挂到本章结束」：按字数算的窗口在 16–20 字章节上会提前 1–1.5s 撤走，那一段画面只剩声音、没有一个字。

**踩到的坑**
1. 纠错只改了 `words`，`segments`（章节用的句子文本）没跟着改：字幕对了，画面上的大字还是「化走」。第一版交付就是这样漏出去的——**SRT 对不代表片子里对，必须抽帧看图**。补 `applyToSegments`，句子按词重建。
2. `execFile` 没有 `input` 选项，喂不了 stdin；拼音查询自己开管道。
3. 本机 python 的 stdin 编码是 cp1252：`json.load(sys.stdin)` 把中文解成乱码，pypinyin 查不到就原样返回，看着「同音」其实没验。改成读写 `sys.stdin.buffer` / `sys.stdout.buffer`。
4. 数字类一开始太宽，模型把「三秒」改成「3秒」被当成纠错放行；同时「打回」被算进质检失败项——校验器拦住错改是它该干的事，不该判不过。两条都改。
5. 同一素材三次转写分别给出「检,」「减。」「化」：低置信片段走 temperature fallback，转写不是逐字节可复现的。**只靠模型会漏**，所以确定性的一半（术语表）必须在。
6. 术语表命中项没带 `verified` 字段，bot 在群里把「undefined」念了出来。

**实测**（24.93s → 16.96s，511 帧，5 章）
- 错字：术语表 2 处（化→划、减→剪）+ 模型 1 提案 0 采纳，打回 1 处（三→3），待确认 2 个（「做」「视」，其实识别对了，只是低概率）；错字治理 10.1s。
- 关掉模型只跑术语表，这条转写照样修干净（回归脚本在 `.test/`，不入库）。
- 抽帧 6.9s、逐帧渲染 83.9s（0.20× 实时）、质检 6/6；同参数另一跑 46.0s（0.37×），本机负载波动大。

**实测**
- 光轨 9:16：1080×1920，508 帧，16.96s，抽帧 5.2s、逐帧渲染 67.6s（0.25× 实时）、17.8 MB、质检 6/6。
- PPT 底座 9:16：1080×1920，17.10s，渲染 23.1s（含 64 条遮罩带，比纯硬边多约 5s）、−17.2 LUFS、质检 6/6。
- 3:4 回归：PPT 底座 5 章 14.7s，光轨静帧逐像素一致。

## 里程碑 7 · 断行落在词边界上（2026-11-20）

章节卡和大字一直切在词中间：「很多人做口播**视 / 频**最大的问题」。根因不是排版算法，是**断点来源**——按字数硬切。

**为什么不能直接用 whisper 的词级时间戳**：whisper 对中文常常一词只给一个字（「视」「频」分开、「说」「白」「了」分开），按它的词边界断≈按字断。词边界得自己算。

**零依赖分词 + 领域词表**
- `src/segment.mjs`：Node 自带的 `Intl.Segmenter('zh', word)` 打底，再用词表把 ICU 拆碎的单字合回整词。ICU 不认识视频黑话：「口播」→ 口|播、「划走」→ 划|走了、「这件事」→ 这|件|事。
- 词表 = `config/terms.json` 的 `hotwords` + `terms[].to`（口播 / 划走 / 完播率 / 光轨 / 气口…）+ 内置几条。客户加行业词就是往术语表加一行。
- 试过 `segmentit`（jieba 词典的 JS 移植，装完 15.7MB）：这条素材上输出和 ICU **一模一样**——它的词表里同样没有「口播」「划走」。装完就删了，仓库仍然零依赖。

**断行规则**（两个模板共用一份）
1. 断点只能落在词边界；
2. 行数取「刚好装得下」的最少行，各行长度尽量均衡；
3. 孤行治理：末行不到半行时从上一行借一个词；
4. 行首禁则：`的/了/着/过/吧/呢/吗/啊/呀/嘛/地/得` 不许起行，并回上一行——那一行宽一个字，由字号吸收。

**接线**
- PPT 底座直接排 ASS：`wrapHead` 用 `wrapWords`，删掉按字数兜底那条路；章节卡字号改成按最长行缩（11 字 × 84px 会顶出安全区，缩到 79 正好），否则行首禁则会把它撑出去。
- 光轨：`scene.mjs` 把每章的 `words` 写进 scene.json，画布引擎按词断行；老 scene 没有 `words` 就退回按字，向后兼容。

**机器检查**
`node scripts/check-wrapping.mjs`：9 句 × 7 种宽度 = 63 条断行，断言「拼回去 === 原文」且「每个断点都在词边界上」。反向验证过——同一段用按字数硬切喂给它，它报出断点 7 和 14，正是「视/频」那两刀。

**实测**（同一素材，24.93s → 17.0s，511 帧，5 章）
- PPT 底座 3:4：渲染 7.3s、−17.2 LUFS、质检 6/6。
- PPT 底座 9:16：1080×1920、渲染 9.2s、−17.2 LUFS、6/6。
- 光轨 3:4：1080×1440、逐帧渲染 50.2s（0.34× 实时）、−17.1 LUFS、6/6。
- 光轨 9:16：1080×1920、逐帧渲染 50.0s（0.34× 实时）、17.0 MB、−17.1 LUFS、6/6。
- 光轨两跑第 1 帧 SHA256 相同（`461861a9…`）：这一轮没有破坏确定性。

**踩到的坑**
1. 换分词器不等于解决问题。把 ICU 换成 jieba 系，领域词照样被拆——词表才是那一层。
2. 行首禁则会让一行变宽一个字，而 PPT 章节卡是固定字号：不跟着缩字号就顶出安全区。字号得由最长行决定。
3. 光轨的字号本来就是「按最长行算的」，同一个规则在画布那边零代价——规则一样，代价不一样，收尾要分别验证。

## 里程碑 8 · 分段缓存：改一句只重渲那一句（2026-11-20）

光轨 0.34× 实时，60s 成片三分钟——而客户改的通常是**一章里的一个词**。这一轮把「改一句整条重跑」变成「只重渲那几帧」。

**怎么算「哪几帧变了」**（`src/render-cache.mjs` 的 `planPatch`）
- 全局字段（模板 / 引擎哈希、画幅、帧率、成片时长、配色、HUD 文案、章节刻度、人物分段、声波）任一变化 → 整条重渲。声波尤其重要：音频一动，光轨整条都不一样。
- 只有某几章的大字或字幕卡变了 → 取它们的显示区间（前后各留 2 帧淡入余量）。
- 改动覆盖超过 45% 的帧 → 也整条重渲，别为了省时间拼一堆碎片。
- 一模一样 → `reuse`，连渲都不渲。

**怎么拼回去**：切头（流拷贝）+ 新渲的一段 + 切尾（流拷贝）→ `concat -c copy`。母版是 FFV1 `-g 1`，每帧都是关键帧，所以切是**无损且精确到帧**的。

**踩到的三个坑**
1. **切片别重编码。** 第一版用 `trim` 滤镜重编码 FFV1，17s 的片子切两刀要 24s——比重新渲还贵，于是「分段缓存」只快了 25%，等于白做。改成流拷贝（`-frames:v` / `-ss` + `-c copy`）后切两刀 1.0s，逐帧 md5 校验完全一致。
2. **别把「浏览器启动」当成本。** 中途怀疑固定开销有 28s，实测 `--mode info` 1.4s、渲 1 帧 1.6s、渲 11 帧 2.2s——启动开销根本不是问题，慢的是切片。先量再优化，别猜。
3. **GPU 着色器有 ±1 级舍入，而且不是稳定复现。** 校验时发现「拼出来的 ≠ 整条重渲」，逐帧查下去：同一区间连渲两次完全一致，但换一个渲染起点就有几帧差一个最低位（PSNR 114 dB）。所以断言拆成两条——**改动之外必须逐帧 md5 完全一致**（那是切出来的，必须精确），**改动之内按逐帧 PSNR 判**（判「是同一张画」，不是「同一串字节」）。

**自检**：`node scripts/check-patch.mjs --group <群 id>` —— 四条全过才叫接上了。

**实测**（24.93s 素材 → 17.03s 成片，511 帧，光轨 3:4，改第 4 章「划走」→「溜走」）
- 判定：`patch`，第 311–389 帧（15%）受影响。
- 分段重渲 **11.0s**（79 帧）vs 整条重渲 **40.8s**（511 帧）——省 73%。
- 改动之外的 432 帧：和旧母版**逐帧 md5 完全一致**（真的是切出来的）。
- 改动之内的 79 帧：和整条重渲**逐帧 PSNR = ∞**（这一跑里连一个最低位都没差）。
- 同一场景再跑一次：`reuse`，连 Chrome 都不启。

**端到端补一刀**（这一轮最值钱的教训）
只缓存「逐帧渲染」不够：第一次接完，改一句要走 39.1s，而整条重渲才 66.0s——省的那点渲染时间全被别的东西吃回去：
- 一模一样的重跑仍然是 27.9s（抽帧 6s + 切音/包络 4s + 编码 20s 一步没省）。
- 改一句的重渲只有 6s，但整条流程 39s，**编码是新的瓶颈**（约 25s）。

所以缓存要按指纹分三层：
1. **成片层**：scene + 模板哈希都没变、成片还在 → 直接交回上一版，**0.01s**。
2. **中间层**：抽好的源帧（按 scene.person + 素材指纹）、切好的声音与包络（按 plan + 素材指纹）都进群缓存，改一句只重做后面的事。
3. **帧层**：只重渲变化区间，其余从母版流拷贝切。

**端到端实测**（17.03s 成片，511 帧，光轨 3:4）
- 第一次出片（冷）：66.0s。
- 一模一样再跑：**0.01s**（改前 27.9s）。
- 改一句：37.2–39.1s（重渲 6s + 切片 1s + 混音 2s + 编码 ~25s）。

## 里程碑 9 · 说一句改一处重跑（2026-11-20）

上一轮的引擎层已经能「只重渲那一处」，但群聊里 `revise` 还只会说「收到，记下了」——客户看不到的能力等于没做。这一轮把最后一句话接上：**用户说改哪句 → 定位到词 → 只改文本 → 包装重出**。

**三个决定**
1. **不重跑转写。** 剪辑结束时把词、句、时间线、字幕卡落到 `groups/<id>/pipeline.json`；升级前的老群从产物反推（`plan.json` 旁边就是 `transcript.json`，字幕卡按词和时间线重建）。所以接这个功能不需要客户把片子重出一次。
2. **匹配摊平成字符流。** ASR 的「划走」常是两个词：「划」+「走了。」。按词匹配永远找不到，摊平后能跨词命中；等长替换按原词边界摊回去（逐字落点不动），不等长时整段塞进起始词、剩下的字留在最后的词里——不丢字，也不假装对齐。
3. **说不清就问。** 一句话里同一个词出现两次、或者这条片子里根本没有，制片人把位置和相近词列出来问清楚，不猜着改。

**自检是硬约束**：词数不变、每个词的起止时间一个不动、改动只能落在被匹配的词上。任何一条不满足就中止并如实说，不静默改坏时间线。`node scripts/check-revise.mjs` 跑 24 条（解析 7 / 定位 6 / 改字 6 / 断言 3），用合成词流，不依赖素材。

**实测**（两条真跑：老群 `talk-06sbg` 与新建群 `group-0fvtq`，光轨 9:16，17.0s，511 帧，第 4 章「划走」→「溜走」）
- 判定 `patch`：第 311–389 帧（15%）受影响，只渲 79 帧。
- 重渲 10.4–11.1s；改一句整条 48.7s（老群）/ 57.1s（新群），质检 6/6。
- 成片、SRT、`scene.json` 三处的字一致（成片抽帧 12.5s 看到「就溜走了」，「溜」正在翻白）。
- 「重跑」不说改字 → `reuse`，母版和成片都复用，连 Chrome 都不启（4.1s 走完含质检）。
- 换模板也成立：PPT 底座 9:16（ffmpeg 引擎，没有分段缓存）改一句整条 11.4s，章节卡、字幕、成片三处都是「溜走」，质检 6/6。

**踩到的三个坑**
1. **SRT 只在剪辑那一步写。** 改完字片子里是「溜走」，交付的 SRT 还是「划走」——上一轮的教训是「SRT 对不代表片子里对」，这是它的镜像：片子里对，交付的清单不一定对。修在包装：字幕按最终文字重写，任何路径（首出 / 改一句 / 重跑）交付的都是同一份字。
2. **目标时长的阈值两处不一致。** 制片人按 15% 判「达标」，质检按 12% 判——17.04s 对 20s 正好落在缝里，群里同时出现「定了」和「不通过，差 -3.0s」。改成同一个 `TARGET_TOLERANCE`（0.12），重出时按当前时间线重算，不读存下来的旧判断。
3. **改完 import 没跑 `node --check` 就重启。** `toSRT is not defined` 把群打成 `blocked`，之后再说「重跑」会被「在跑，跑完我报」接住——卡住的群得把 phase 还原。改一行代码也要先 --check，再重启。

**剩下的瓶颈**：改一句 48.7–57.1s 里，渲染只有 10–11s，**编码 33–35s**。本机 x264 软编 1080×1920（NVENC 有编码器没 GPU）。下一步按机器能力选编码器，或只重编变化段的 GOP。

## 里程碑 10 · 改一句只重编那一格（2026-11-20）

上一轮「改一句」只解决了画面：渲染只重渲 79 帧，编码还是整条重来 33–35s，占改一句总时长的一半以上。这轮把编码也切开。

**做法**：成片按 32 帧一格落关键帧（`-x264-params keyint=32:min-keyint=32:scenecut=0`）。改到的帧扩到整格（311–389 → 288–415，128 帧），只重编这一格，前后从上一版成片 `-c copy` 切出来拼回去；关键帧栅格随片子一路传下去，所以第二、第三次改一句还能接着切。

**为什么不是「缓存编码片段」**：先试过按格缓存每段编码再 concat，整条重编反而从 30.7s 涨到 54.5s（每段都要重新起 x264、单独跑 VBV），而上一版成片本身就是最好的缓存——只要切点落在关键帧上。

**拼错比慢更糟**，所以三道断言：

1. 切之前先查上一版成片在栅格位置上真的有关键帧（mp4 的包是解码顺序，关键帧位置要用 pts×fps 换算）；没有就整条重编，不硬切。
2. 每段流拷贝切完数帧数（`nb_read_packets`，mkv 的 nb_frames 不可信），少一帧就中止。
3. 拼完把上一版和新片各解一遍（framemd5，并行），窗口外的帧必须逐帧一致；不一致就整条重编，不交错位的片子。

**实测**（24.93s 素材 → 17.0s 成片，511 帧）：

- 首出：渲染 47.0s + 编码 33.1s（整条重编，比原来的 30.7s 多 2.4s——多出来的就是关键帧栅格）。
- 改一句：**31.4s**（原 48.7–57.1s），其中重渲 11.9s、编码 14.2s（只重编 128 帧 + 逐帧对账）、质检 6/6。
- 同一版里接着再改一次（「人群」→「大家」）：31.4s，窗口外 383 帧与上一版逐帧一致。
- 自检 `scripts/check-encode.mjs` 14 条全过（栅格 / 只重编一格 / 窗口外逐帧一致 / 老片子不能切时整条重编 / 帧数不对中止）。

**四个坑**：

- 输入侧 `-ss` + 流拷贝是「给到目标时间之前最近的关键帧」。写 `frame/fps`，差 0.0007 秒就退回上一格（32 帧），片子整体错位；要加半帧落在目标格里。
- 单独编出来的那一段若带 B 帧，首帧 pts 从 1/30 起头，concat 按「末帧 pts + 帧长」累计时长会多算一帧，交界处空一格、后面整体错位。改成 `-bf 0` + `-bsf:v setts=pts=PTS-STARTPTS` 把时间戳压到 0 才对齐。
- 验证也用 `-ss` 抽帧会误报：两条片子的 GOP 结构不同，从关键帧解出来的第一帧可能差一帧。最终改成整条顺序解 framemd5 再逐帧比，慢 4s 但结论确定。
- 顺手修了一个老 bug：编码命令里的 `-shortest` 会因为音轨比画面短几帧而悄悄截掉片尾 3 帧。去掉，画面长度由帧数说了算。

## 里程碑 11 · 制片人真的听懂需求（2026-11-20）

群聊里制片人的话一直是模板句填数字，规格是几条正则猜的：平台靠匹配词、时长只认阿拉伯数字（「一分半」直接漏）、模板靠「光轨 / PPT」关键词。这轮把「接需求」接上真模型，同时把「模型能不能说了算」切开。

**做法**

- `src/llm.mjs`：读需求和错字治理共用一个本机模型客户端，配置、超时、失败口径（no-key / http-4xx / timeout / unreachable / bad-json）一套；任何失败都返回 `{ok:false}`，不抛。
- `src/brief.mjs`：把 roster 里的模板（id / 名字 / 支持的画幅 / 时长区间 / 说明）交给模型，要它只回六个字段；`mergeBrief` 逐字段按 **用户原话 > 模型 > 默认** 合成，每个字段记来源（`brief.src`），模型补的进 `assumed`，模型和原话冲突的进 `corrected`。
- **用户原话优先**：先用规则抽出「用户明确说了的」，模型和它冲突就听用户的并在群里说明。时长解析认中文数字：`一分半`→90s、`四十秒左右`→40s、`半分钟`→30s、`别超过一分钟`→60s、`1.5分钟`→90s。
- **校验器说了算**：模板必须是 roster 里 `ready` 的 id；画幅必须是这个模板真做过的（要 16:9 而模板没做，卡片照实标出来，确认后按模板画幅出并说明）；时长夹在 8–300s；模型给的非法值退回默认，不硬吃。
- **群里怎么说**：先一行「制片人在读需求…」（同一个 bot 开口后自动收起），然后确认卡 + 「我按你说的填好了 / 推荐模板：… / 我替你定的：… / 模型读岔了… / 模型没接上：timeout，这版是规则填的」。
- 界面：确认卡多一条「模板理由」（整行铺开）；字段是奇数时最后一格铺满整行，不留半个空格子。

**实测**

- 四句话 3.7–5.7s（本机 OpenCodex，`gpt-6-luna--fast`）。「明天发视频号，剪到四十秒左右，口播为主别搞太多花字，有稿子在桌面」→ 视频号 / 9:16 / 40s / PPT 底座 / 有稿，群里只说「我替你定的：画幅 9:16」。
- 「横屏 16:9，三分钟，做成 PPT 那种」→ 卡片标「3:4 · 1080×1440（PPT 底座 没有 16:9）」，群里给「要 16:9 我另排一版布局，时间线不用重剪」。
- 全链路一条：说「发抖音，大概二十秒，用光轨，竖屏，我没稿子」→ 卡片 抖音 / 9:16 / 20s / 光轨 → 成片 **1080×1920**、17.03s、511 帧、质检 6/6；制片人如实报「到不了 20s，差 3.0s，要凑得压到 0.85× 语速，我不做这个决定」，不硬凑。
- 自检：`check-brief.mjs` 47 条、`check-asr-fix.mjs` 33 条，全过。写 check-asr-fix 时顺手抓到一个真 bug（见下）。

**四个坑**

1. 「没有稿子」里含「有稿」——正则顺序反了会把没稿读成有稿。旧代码就是这样，顺手修了。
2. 校验器的「同一词位只认一次」只在建候选时查，而 `seen` 要到采纳时才填——同一个词位两条提案会双双标成「采纳」，报告说改 2 处、实际只落地 1 处。补了一次拦截，这是 check-asr-fix 发现的。
3. headless Chrome 开着 SSE 永远不会进入「加载完成」，`--screenshot` 会一直挂着不退出（这次实测两分钟没落盘）。截图改走 CDP：开标签 → 等页面画完 → `Page.captureScreenshot`，写完即杀进程。
4. 模型会为了迁就模板的时长区间改用户说的数字（「四十秒」→45s，因为 PPT 底座最短 45s）。所以时长以用户原话为准，模板区间只在群里提醒；这也说明「模型提判断、规则校验」这个分工不能省。

**下一步**：资产层（bot 名册 / 模板库 / 术语表）从「只能改文件」做成后台页；剪辑、包装、质检的话接模型（成本与延迟由用户定）；读需求这一步可以换更稳的档位试。

## 里程碑 12 · 资产层：术语表能改，还带三道门（2026-11-20）

前台是群聊，背景层是资产。这一轮把「术语表只能改 config/terms.json」这个缺口补上，
并且没做成一个能随便填的表单——客户改错了，坏的是每一次转写。

**做法**

- `src/assets.mjs`：资产层的唯一来源。`readTerms`（带 `rev` 文件指纹）、`validateTerms`（形状门）、`auditTerms`（同音门，拼音可注入）、`writeTerms`（临时文件 + rename）、`serializeTerms`（和手写格式对齐的序列化器）、`trial`（试验台）、`botRoster` / `templateLibrary`（只读视图）。
- 三道门：**形状门**（缺 to / 缺 from / from 等于 to / 类型不合法 / 重复，每条指到 `terms[3].from[1]` 这一格）→ **同音门**（`kind: homophone` 必须真同音，不同音的只能登记成专有名词）→ **缓存门**（存盘后 `resetLexicon()`，否则断行还在用旧词）。
- 三条接口：`GET /api/assets`、`POST /api/assets/terms`（带 `rev` 对账，别处改过返回 409）、`POST /api/assets/terms/trial`（拿草稿跑，不用先存）。
- 页面 `web/assets.html`：名册 / 模板库 / 术语表三块，一行一个的台账排法（没有卡片墙）。术语行内可编辑，热词增删走 chip，下面是试验台。群聊左栏脚上「资产层」进。
- 试验台同时报两条口径：「按词切」（生产路径，真 `applyTerms`）和「字面」（客户脑子里那版）。两边不一致时直说——「口拨」在原文里有，但 ICU 把它切成「口」「拨」，生产路径上要等 whisper 把它当一个词才会改。

**实测**

- 术语表现在 21 热词 / 13 条目，同音门跑 **28 条拼音全过**（修完之后）。
- 试验台：「观众三秒就画走了」→「观众三秒就**划**走了」，命中 1 处（后接「走」的拆词条目），字面 1 处（2 条规则都指向这里）。
- 接口：加一条 `观点 → 观众` 的「同音字」→ **400**，理由带拼音「guandian / guanzhong，不同音，只能登记成专业名词」；缺 `to` → 400 指到 `terms[13]`；原样存回 → 200 且 rev 不变；拿旧 rev 再存 → **409**。
- 存盘幂等：内容不变的一次存盘 **0 行 diff**；内容真变的一次只剩 3 行改动。
- 自检 `scripts/check-terms.mjs` **52 条**（解析 5 / 形状门 11 / 同音门 8 / 试验台 9 / 存盘 11 / 接线 8），同音门用假拼音喂、存盘写临时目录，不联网也不碰仓库术语表。

**五个坑**

1. `applyTerms` 是确定性替换，**它不验拼音**——所以一条标着「同音字」但根本不同音的条目照样会生效，把片子里写对的词改坏。同音门第一次跑就在自己的表里抓到 2 条：`转长` / `传场` → `转场` 读 zhuǎnzhǎng / chuánchǎng，已改成 `kind: term`。
2. 手写 JSON 的排版没法用规则复刻（热词 10+11 分行，宽度反而不一致）。第一版存盘用 `JSON.stringify(…, 2)`，把 157 行全改了；改成按视觉宽度 88 的序列化器后，第一次存盘只剩 3 行真改动，第二次 0 行。
3. 术语表存了但断行还用旧词：`segment.mjs` 的 lexicon 是模块级缓存，必须显式 `resetLexicon()`。界面说保存成功、效果没变的谎最贵。
4. 试验台如果只按分词跑，「口拨」这种被切碎的错写永远显示「没命中」，客户会以为术语没用。补字面扫描，并把两边为什么可能不一致写清楚，比给一个漂亮的假答案强。
5. 名册一开始用 `...b` 全量下发，把 skill 名发给了浏览器。skill 是内功、不是产品形态，接口里只给界面真会显示的几栏。

**下一步**：首出整条编码 33.1s 仍是最大块（本机 x264 软编，NVENC 驱动太老）；光轨「字藏人物身后」缺 Windows 人物蒙版方案；剪辑 / 包装 / 质检的话接模型要用户先定成本与延迟；真实口播素材还没进来。


## 里程碑 13 · 近音 / 跨词纠错 + 折光真素材走完整个产品（2026-11-24）

**做了什么**

- **近音纠错**（`kind: near`）：同音字覆盖不了「千→天」这种错——韵母 ian1 一致、声母 q/t 不同，不是同一个音。
  放行条件写死三条：拼音全等之外还要**韵母+声调完全一致、声母不同**，**改动范围前后 3 个词内有一个置信 < 0.65 的词**（ASR 自己就在犯嘀咕），
  全片最多 2 处。`tools/pinyin.py` 多返回 `ini` / `fin`（`Style.INITIALS` / `Style.FINALS_TONE3`），校验器按字逐个比。
- **跨词重排**（`{"i","n","to"}`）：把 n 个相邻词的文字合起来重排，**总字数不变、按原词字长重新分配**，标点留在原位，词数与每个词的起止时间不动。
  ASR 把词切错位置时只能这么改，换一个词会撑破字幕卡。
- **温度固定 0**（`src/llm.mjs` 的 `temperature`）：纠错是抽取任务，之前不设温度，同一段素材两次给的结果不一样，一次甚至直接回「没有要改的」。
  另外第一次 0 提案且还有低置信词时再读一遍（第二遍照样过校验器）。
- **语义审读的 token 预算**（`SEMANTIC.maxTokens` 1400 → 2600）：26 张字幕卡时 JSON 会被截断，`reading-unverified` → 直接判不通过。
  截断等于没查，宁可多花几百 token。

**真素材端到端**（群 `03-0is5s`，素材 720×1280 / 72.17s，需求「竖屏抖音口播，60 秒左右，用光轨模板」）

- 开工到交付 **14 分 06 秒**：转写+纠错 176s、抽帧 33.2s、逐帧渲染 393.0s、编码 165.9s、质检 54s。
- 成片 68.40s / 2052 帧 / 1080×1920 / 67.4MB / −14.8 LUFS；质检 **13/17**。
- 纠错只落 1 处，但正是语义层拦过的那处：47.27s「花一千的时间」→「花一天的时间」。
  证据：韵母 ian1 一致、声母 q→t，同段「一」置信 0.54。SRT 与画面大字同步改（`applyToSegments` 按词重建句子）。
- 四个 bot 的结论都是自己下的：剪辑报「超 8.4s，得靠内容删减或变速」；包装报渲染/编码秒数；质检逐项带帧号；制片人按实际时长交付并写清差额。

**四个真问题（下一轮的事）**

1. **目标 60s 到不了 68.4s**：剪辑只会删气口，不会删内容。需要「按目标时长选句删」的能力。
2. **38.24s 重复句**「但是AI来去做内容」：ASR 重复，EDL 没去重。
3. **低置信 25/251 = 10%** 超 8% 上限：真素材上 `small` 不够用。
4. **大字压在人物身上、章节卡断行留孤字**（「真正赚钱有 / 几个」）：断行的借词规则没覆盖单字孤行。

**复看折光成片（改了我原来的判断）**

抽帧看 8s / 30s / 45s 三帧：折光的大字同样压在人物身上，它的质感来自**图形段**——
eyebrow 小标、信息卡（带柱状图）、竖切分屏 5 栏、日期 chip、字幕关键词黄色高亮、底部细进度线。
所以「对照折光 = 先做人物蒙版」这个方向是错的；蒙版是填空题，主考题是图形块库。详见 `docs/MATTE.md` 末尾。

**三个坑**

1. 拼音批量查询的返回顺序是「一条提案两项、交错排列」（`flatMap`），按「前半是原文、后半是新文」取值会把「瓶→盆」比成「ping vs yiqian」。
   这种错会静默放行或静默打回，只有真素材才暴露。
2. 只给模型「四类错」的清单，它会跳过读不通的整句。加了「先把词序列连起来读一遍，把读不通的句子挑出来」之后，同一段素材才稳定报出「一千的时间」。
3. 换代码后老群里的报告还指向旧文件（服务进程里缓存了 group.meta）。改了报告要连 `artifacts.report` 一起换，否则界面显示旧结论、盘上是新结论。

**补记（同一天，交付后两小时）**

- **大字断行挪到数据层**：首版 `templates/lighttrail/film.js` 自己按字数硬切，切出「会做内容的人 / 少」单字孤行；
  而 `src/segment.mjs` 的 `wrapWords` 早就有「均衡 + 末行借词 + 行首禁则」。现在 `scene.mjs` 用 `wrapWords` 把 `lines` 算进 scene.json，
  渲染器只画 `b.lines`（没有才回落）。重渲后：「真正赚钱 / 有几个」「会做内容的 / 人少」「一天做出 / 一周工作量」。
  代价是一次全量重渲（模板变了，帧级缓存整条失效）：渲染 267.4s（0.26× 实时）+ 编码 92.7s。
- **一次卡死没归因**：重渲到第 1830 帧，headless Chrome 停住 12 分钟无进展（进程还在、日志不动）。
  杀掉无窗口的 chrome 进程重渲才过，第二遍 267.4s 顺利完成。渲染器**没有卡死看门狗**——这是下一轮要补的：
  超过 N 秒没有帧进度就杀浏览器并如实报「渲染在第 X 帧挂住」，而不是安静地停着。
- 顺手把「大字断行」的规则统一到一处：PPT 底座和光轨现在都走 `src/segment.mjs`，渲染器里那份 `splitLines` 只作兜底。

## 里程碑 14 · 渲染看门狗：卡死不报错的那种错（2026-11-24）

**为什么做**

光轨挂在无头 Chrome 里，它挂掉的方式是「不报错」：昨天重渲停在第 1830 帧（共 2052），进程还在、日志不动，
12 分钟没人发现。超时一刀切又不行——正常一次整条渲染就要 5–7 分钟，慢和死分不开。

**做法**（`src/watchdog.mjs`）

- 判活看两个信号：子进程 stdout/stderr 有输出；产物文件（母版 mkv / 采样 json）在长大。
  渲染器 60 帧才打一行日志（1080×1920 约 12s），只看日志会把一条正常的片误杀。
- 静默超过 `VISION_BOTS_STALL_MS`（默认 90s）判卡死：`taskkill /T /F` 杀整棵树
  （node 渲染器 + 无头 Chrome + ffmpeg），删掉这一次的半截母版，重跑一次；
  还卡就报「静默多久 / 最后一行输出 / 试了几次」，不说成「慢」。
- 退出码非 0 的失败不重跑——那不是卡死，原样报错，掩盖真错更糟。
- 三个入口都过：逐帧渲染（90s）、静帧与版式采样（放宽到 3 分钟，它们本来就安静地跑）。
- 改写时踩到一个真问题：原 `run()` 把 `LIGHTTRAIL_FFMPEG` 注给子进程，换成 `runGuarded` 后
  必须显式传 `env`，否则渲染器一出生就 ENOENT（本机 ffmpeg 不在 PATH 上）。

**验证：拿 22 章那版（自测 01 交付的 scene，2052 帧）整条重跑**

- 渲染 331.2s（0.21× 实时）、编码 177.4s（整条重编 x264 veryfast）、68.40s / 1080×1920 / 2052 帧 / 70.69MB / −14.8 LUFS。
- 看门狗**零触发**：第 1830 帧在 293.9s 顺利过去——上一次就停在这里。
- 与 11-23 交付那条比：帧数 / 时长 / 编码器 tag / 响度四项一致；整条 PSNR 18.3 dB 是**版式差**
  （旧模板 1674 字节、轨道穿脸、字幕没 pill、大字 3 行），不是错位。这一版内容也是旧的（错字治理前），只验链路不交付。
- 卡死侧用真的 vendor 渲染器验：给它一个起不来的 Chrome，`/frame` 永远不来，看门狗 4s 判死并杀掉整棵树。

**四个坑**

1. 只看日志会误杀：先按「静默」写，一条正常渲染就会在 60 帧的日志间隔里被砍。产物在长大必须算活。
2. `taskkill /T /F` 是必须的：只杀父进程，孤儿 Chrome 会留在后台继续占显存。
3. 重跑前不清半截母版，就有把它当结果的机会；删除这一步不能省。
4. 老 scene 不能直接喂新引擎：22 章那版的 scene 没有 `subs` 字段（字幕后来才搬进 scene），
   新 `film.js` 读 `S.subs.findIndex` 直接崩。可以补字段，不许改内容。

**下一步**：EDL 去重（38.24s 那句重复）→ 图形块库（eyebrow / 信息卡 / 分屏 / chip / 关键词高亮 / 进度线）。


## 里程碑 15 · 每个 bot 一份配置 + 剪辑表 v2（2026-11-24）

两条改动一起做，因为「剪辑怎么剪」本来就不该是一个全局常量：它是剪辑这个 bot 的判断口径。

**每个 bot 一份配置**（`config/bots/<id>.json` + `src/bots/config.mjs`）

- 一个 bot 一个文件：模型、温度、maxTokens、maxSteps、timeout，加上这行的专业参数
  （剪辑的剪辑点阈值/停机目标/去重规则，质检的时长容差，制片人的派活提醒阈值）。
- 模型别名 `fast` / `smart` 映射到 `llm.local.json` 的两档，也可以写完整模型名单独走。
  `llm.mjs` 的 `callProfile(botId)` 是唯一解析点，`agent/loop.mjs` 拿到什么用什么。
- 单 bot 覆盖：`VISION_BOTS_<ID>_MODEL` / `_TEMPERATURE` / `_MAX_STEPS`；`VISION_BOTS_CONFIG_DIR` 挪配置目录。
- 坏配置不炸：类型不对、越界、JSON 解析失败都退回默认值，并记进 `configProblems()`（哪份文件哪一条）。
- 名册里删掉了 `model: 'same'`：模型是配置，不是身份。资产页显示每个 bot 实际连的模型。

**剪辑表 v2**（`src/plan.mjs` + `src/energy.mjs`）

- 删词有理由：`repeat` / `filler` / `mistake`（外部指定），每条带文本、理由、位置，进 `plan.json`。
  自动规则的分寸：重复要连续 ≥3 词、≥4 字、间隔 <0.8s（隔一秒是强调）；口头语分强弱
  （「嗯/啊」一侧有停顿就删，「那个」必须后面有停顿——「那个人」是指示词）；删掉超过全片 30% 退回口头语。
- 停机按标点分级：句号 0.30 / 逗号 0.22 / 删词接缝 0.08 / 无标点 0.20。
- 接缝吸附：从 16k WAV 算 5ms/20ms 的 dB 包络，在名义刀口前后 250ms 找连续 25ms 的安静段，两侧各让一半。
  找不到安静段就用名义值——不为吸附多留 100ms，也不许把切口算反。
- 被剪掉的词不进字幕（按「中点在不在保留区间」判）。否则音频删了、字幕还挂着，等于说了两遍。

**真素材验证**（折光那条 72.17s / 251 词，用已交付的 transcript 重算，不重转写）

| | 成片 | 刀口 | 删词 | 字幕卡 |
|---|---|---|---|---|
| 已交付（v1） | 68.40s | 10 | 0 | 26 |
| v2 | **65.87s** | 11（气口 9 + 接缝 2） | 1 处（重复 9 字 / 2.38s） | **25** |

抓到的正是质检一直在报的 38s 那句「但是AI来去做内容」（第二遍，源时间 39.94s）。字幕覆盖率 100%，0 缺字。
离 60s 目标还差 5.9s——删词和压停顿只能拿回 2.5s 左右，剩下的差额要靠**选句删**（整句不要），
那是产品决定（删哪句、删完逻辑还通不通），不是算法能替用户定的。

**踩到的两个坑**

1. 能量吸附在「安静区比目标停顿窄」时会把切口算成负数（to < from），结果是既不剪也不留。
   现在只要安静区不够宽就退回名义值，并且最终校验 `back > out`。
2. 第一版重复检测把「位置」记到了第一遍身上，报告里指错地方。删的是后一遍，位置就得指后一遍。

**自检**：`check-bots` 27 条（每个 bot 独立 / 坏配置退回默认 / 环境变量只覆盖一个 / 循环真的用上配置）、
`check-plan` 27 条（重复 / 口头语 / 歧义指示词 / 口误 / 停机分级 / 能量接缝 / 不切词 / 不丢字 / 真素材回归）、
`check-agent` 35 条。`check-patch` 仍未通过：仓库里 5 个老母版的 scene 都是 `subs` 之前的格式，
和本次改动无关，要等下一次重出片生成新母版。

## 里程碑 16 · 大字跟着口播换（2026-11-24）

**问题**：口播已经说到下一句，屏上大字还停在上一句。用户原话：「不要说到下一段了，字幕还在上一段」。

**根因**：大字的上屏单位是「段落」（2–4 句、6–7 秒、最长 16 秒）。段落是给「不抖」做的，
但代价是段里句子走完了字不动：改前 12.0s 那一帧，字幕「AI模型做AI工具的」，大字还挂着「今天给大家泼冷水」，
最长一条挂了 8.9 秒、跨 4 张字幕卡。试过「按 whisper 段切」，更糟——whisper 的中文段能塞进 4 张卡。

**改法**（`src/headlines.mjs` + `templates/lighttrail/scene.mjs`）

- 上屏单位 = **字幕卡**：大字区间就是这张卡的区间，字幕换卡的那一帧大字一起换，字幕一撤大字也撤。
  段落（01/10）留在光轨刻度上，不再决定大字什么时候换。
- 标题校验比段落标题更严：**100% 的字来自本卡**（不是 80%）、≤8 字、不许连接词开头、
